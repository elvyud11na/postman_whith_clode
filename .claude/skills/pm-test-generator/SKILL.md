# Генератор pm.test скриптов

## Как работать

1. Определи, что дано на входе:
   - Пример JSON-ответа
   - Описание/схема эндпоинта (метод, статус, поля)
   - Существующий запрос из Postman-коллекции (через MCP)
2. Если данных недостаточно (неясен статус-код, обязательность полей) — задай 1-2 уточняющих вопроса, не придумывай.
3. Строй тесты по стандартным блокам, включай только применимые:
   - Статус-код (200/201/400/401/403/404/422 — в зависимости от контекста)
   - Время ответа (response time is less than N ms) — только если явно попросили или это часть чек-листа проекта
   - Структура ответа (наличие ключевых полей)
   - Типы полей (string/number/boolean/array)
   - Значения-константы, если применимо (например, статус всегда "success")
   - Заголовки ответа (Content-Type и т.п.) — только если релевантно
4. Пиши тесты на chai-подобном синтаксисе Postman (pm.test + pm.expect), без внешних библиотек.
5. Каждый pm.test — отдельная проверка с понятным названием на русском или английском (следуй языку остального проекта).
6. Если запрос доступен через MCP — предложи сразу вставить тесты в вкладку Tests этого запроса, а не просто вывести текст.

## Формат вывода

```javascript
pm.test("Status code is 200", function () {
    pm.response.to.have.status(200);
});

pm.test("Response has required fields", function () {
    const jsonData = pm.response.json();
    pm.expect(jsonData).to.have.property("id");
    pm.expect(jsonData).to.have.property("email");
});

pm.test("Email field is a valid string", function () {
    const jsonData = pm.response.json();
    pm.expect(jsonData.email).to.be.a("string");
});
```

## Что НЕ делать

- Не придумывай поля, которых нет в предоставленном примере/схеме.
- Не добавляй проверки производительности без запроса пользователя.
- Не дублируй одинаковые проверки в нескольких pm.test — одна проверка = один test-блок.
