# Coverage-отчёт по коллекции

## Как работать

1. Определи источники сравнения:
   - Postman-коллекция (через MCP — прочитай список запросов, их Tests-скрипты, описания)
   - Эталон: OpenAPI/Swagger-спека, или список эндпоинтов, который дал пользователь
   Если эталона нет — можно оценить только внутреннее качество коллекции (см. пункт 3), без сверки с полным списком эндпоинтов API.

2. Если есть и спека, и коллекция — сопоставь:
   - Какие эндпоинты из спеки отсутствуют в коллекции полностью
   - Какие есть в коллекции, но нет в спеке (могут быть устаревшими или недокументированными)

3. Для каждого запроса, который есть в коллекции, проверь:
   - Есть ли хотя бы один `pm.test(...)` во вкладке Tests
   - Есть ли описание (Description) у запроса
   - Покрыты ли, помимо позитивного сценария, негативные (если это видно по названию/группировке запросов в коллекции)

4. Не выдумывай, что "должно" тестироваться, если это не следует явно из спеки или из структуры коллекции — отчёт про факты, а не про домыслы о бизнес-логике.

5. Формат вывода — сгруппированный отчёт, не сплошной текст. Заверши кратким числовым резюме.

## Формат вывода (пример)

### 🔴 Эндпоинты из спеки, отсутствующие в коллекции
- DELETE /users/{id}
- PATCH /orders/{id}

### 🟡 Запросы без тестов
- GET /companies/withLimit — тестов нет
- POST /users — только 1 тест (статус-код), нет проверки тела ответа

### 🟡 Запросы без описания
- GET /companyById

### 🟢 Полностью покрытые запросы
- POST /auth/login — тесты + описание есть

**Итого:** покрыто 12 из 18 эндпоинтов спеки (67%). У 5 запросов нет тестов, у 3 нет описания.

## Что НЕ делать

- Не считай запрос "непокрытым", если тесты есть, но кажутся тебе недостаточными по глубине — для такой оценки нет объективного критерия, если пользователь не задал свой.
- Не удаляй и не изменяй ничего в коллекции самостоятельно — это отчёт, а не автоисправление.
- Не выводи 100% покрытие, если эталон (спека) не был предоставлен — в этом случае явно укажи, что оценка только по внутреннему качеству коллекции.
